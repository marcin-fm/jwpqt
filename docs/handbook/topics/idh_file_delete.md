# Deleting Files

File > Delete removes the current document's disk file only after successful deletion. JWPqt does not clear the editor first and then hope the filesystem operation worked. Once deletion succeeds, the editor is cleared, making the document visibly different from its former saved source. This differs from merely closing a tab: Close removes the document from the workspace but leaves its disk file in place. See [Closing Files](help:IDH_FILE_CLOSE).

Treat Delete as a disk operation, not an undoable text edit. Confirm the current tab and pathname before using it, especially when multiple tabs or duplicate copies are open. A duplicate tab is a separate in-memory document, but it may refer to the same original pathname; that does not turn deletion into coordinated version management. Save As and Export Copy cannot overwrite a path owned by another open document, yet the safest approach is still to avoid parallel copies when a delete is intended. See [Duplicate Files](help:IDH_FILE_DUPLICATE) and [Saving Files](help:IDH_FILE_SAVE).

If the disk delete fails, the editor is not cleared. Resolve the reported condition before retrying. If the document needs to be retained elsewhere first, create a verified Save As destination or Export Copy before deleting the original. The optional `_BAK` feature preserves a previous version during saves; it is not a substitute for a deletion archive and should not be assumed to exist unless the setting was enabled. See [Backup Files](help:IDH_FILE_BACKUP).

In a browser, the file boundary is different. Opened content is an uploaded working copy in browser storage and Save creates a download; it is not a general local filesystem handle. The native Delete workflow should therefore not be read as a way to delete a file from the user's browser-visible filesystem. Clearing browser site data removes browser working copies and settings, but that is a browser-storage action, not a replacement for desktop file deletion.
