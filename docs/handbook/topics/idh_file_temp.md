# Temporary Files and System Failures

JWPqt protects file replacement by preparing output before it publishes a destination. Native document saving is atomic: a failed encode, write, or final publication does not silently replace the old document with a partial file. The previous-version backup option, when enabled, first preserves the prior destination bytes under the appended `_BAK` name and then publishes the new document. A failure to create that backup leaves the document and old backup intact. See [Saving Files](help:IDH_FILE_SAVE) and [Backup Files](help:IDH_FILE_BACKUP).

This does not mean every pair of files forms one transaction. If the backup has successfully copied the old disk version but final document publication fails, the backup may be updated to the still-current disk version. Treat the diagnostic as authoritative: inspect the existing source and backup before retrying, and resolve disk capacity, permissions, destination availability, or encoding errors. The source does not document a user-facing temporary filename contract for 2.03, so recovery instructions should rely on the preserved destination and `_BAK` behavior rather than guessing a temp-file suffix.

PDF jobs follow the same safety principle. PDF output is written to a temporary file beside its destination and atomically published only after a successful, uncancelled job. Invalid geometry or ranges, cancellation including the final checkpoint, and a destination that becomes an open document during progress cannot destroy an earlier PDF. Application settings, histories, and current projects are also protected destinations. Oversized jobs report an error rather than silently truncating. See [Actually Printing Something](help:IDH_PRINT_PRINTING) and [Page Breaks and Formatting](help:IDH_PRINT_PAGEBREAK).

Projects, recent-file history, settings, and named-session archives likewise avoid replacing corrupt, locked, or externally changed state. A failed named-session save offers Cancel or exit without updating the archive. Interactive JWP recovery is only for a validated damaged source during Open; Revert and project staging remain strict. These choices preserve recoverability without inventing content that could not be validated. See [Common Difficulties Opening Files](help:IDH_FILE_PROBLEMS) and [Working with Projects](help:IDH_FILE_PROJECT).
